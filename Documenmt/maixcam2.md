I MSPM0G3507 与 MaixCAM2 串口通信协议说明（v1.0）

本文可以直接交给代码生成 AI，用于编写 TI MSPM0G3507 与 MaixCAM2 两端的 UART 发送、接收、解析、应答和超时重发代码。以下格式是正式约定。代码不得擅自改变帧头、帧尾、字段顺序或应答格式。

1. 通信对象与总体目标

通信双方为：

TI 单片机：负责整车控制，并向 MaixCAM2 发送任务控制命令。

MaixCAM2：负责视觉检测，接收 TI 的命令，并向 TI 返回命令应答和检测结果。

UART 为全双工通信，因此两端可以分别发送数据。协议采用简单的 ASCII 文本帧，不直接发送 float 变量在内存中的四字节二进制数据。


两端的 UART 参数必须完全相同，并且硬件必须共地。

2. 基本编码规则

2.1 发送 ASCII 字符串

双方发送的都是 ASCII 字符串。例如，TI 发送：

CT1#

UART 线上实际发送的字节为：

0x43 0x54 0x31 0x23

它们分别是字符 C、T、1、# 的 ASCII 编码。

因此：

串口助手测试时使用“文本发送”或“ASCII 发送”；

不要勾选 HEX 发送；

不要直接发送浮点变量的四字节内存内容；

字符串结尾不发送 C 语言内部使用的 '\0'；

本协议不要求在帧后附加 \r 或 \n。

若某个发送接口自动附加 \r\n，接收端应在帧外忽略它们，但正式代码最好关闭自动换行。

2.2 帧头和帧尾

TI 发出的所有帧都以大写字符 C 开头。C 表示 Control/Command。

MaixCAM2 发出的所有帧都以大写字符 V 开头。V 表示 Vision。

所有帧都以字符 # 结束。

因此，两个方向的基本形式分别为：

TI → MaixCAM2：C......#
MaixCAM2 → TI：V......#

# 是唯一的帧尾。接收端只有在收到 # 后，才可以把前面的内容当成一条完整帧进行解析。

2.3 大小写与空格

所有协议字母统一使用大写；

合法帧中不允许出现空格；

帧前、帧中、帧后均不插入中文符号；

字段分隔符必须使用英文半角逗号 ,；

帧尾必须使用英文半角井号 #。

3. 数值表示规则

协议中有两类数值。

3.1 整数

任务开关、检测开关、模式编号等离散数据使用十进制整数，不带小数点。

例如：

0
1
2
12

当前协议中：

T、D、M 类型命令后面的数据按整数解析；

开关量只允许 0 或 1；

模式编号的合法范围由模式表规定。

3.2 固定一位小数的有符号数

坐标、偏差、距离和角度等连续量统一发送成带一位小数的十进制文本：

32.3
-32.3
319.8
0.0
-1.0

正式发送端始终保留一位小数：

32     → 32.0
32.34  → 32.3
-5     → -5.0

正数通常不发送 +，负数在数字前发送 -。负号是当前数值字段的一部分，不需要单独增加“正负号字段”。

TI 端建议将这类数解析为“放大 10 倍的有符号整数”，避免依赖 sscanf("%f")：

32.3   →  323
-32.3  → -323
319.8  → 3198

例如变量可命名为：

int32_t x10;
int32_t y10;
int32_t distance10;
int32_t yaw10;

需要浮点数时再转换：

float x = x10 / 10.0f;

TI 解析器必须能够识别负号，并严格检查：

可选的负号 -；

至少一位整数数字；

一个小数点 .；

小数点后恰好一位数字；

随后必须出现协议规定的分隔符 , 或帧尾 #。

截图中的 CY3.32# 是口述阶段的示例。由于后来已经规定所有连续量固定保留一位小数，正式格式应写成：

CY3.3#

4.3 命令执行原则

MaixCAM2 收到命令后必须按以下顺序处理：

找到帧头 C；

收齐数据，直到收到帧尾 #；

检查命令类型是否存在；

按该命令类型检查数据格式；

检查数据范围是否合法；

执行命令，或把系统设置到命令要求的目标状态；

最后发送应答帧。

绝对不能只看到帧头 C，或者只收到一部分字符，就提前发送“成功”应答。

距离的物理单位必须由双方在业务层统一，例如统一规定为厘米。通信层只负责传输数值，不能一端按毫米、另一端按厘米解释。

5.2 found 的命名

口述中把这个字段叫作 sign，但 sign 通常表示数字的正负号，容易与 x、y 前面的负号混淆。

正式代码中统一命名为：

found

含义为：

found = 1：本帧检测到目标，x、y 有效
found = 0：本帧没有检测到目标，x、y 无效

5.3 没有目标或没有距离时

即使没有检测到目标，也必须保持字段数量不变。例如：

VD,0,0.0,0.0,-1.0#

约定：

found = 0 时，TI 不得继续使用该帧中的 x、y 控制执行机构；

distance = -1.0 表示距离无效或当前没有距离数据；

如果检测到了目标但暂时没有距离，也发送：

VD,1,-32.3,319.8,-1.0#

禁止有时发送三个数据、有时发送四个数据。字段数量必须始终固定。

因此，截图中的：

VD,1,32.3,319.8#

只包含 found、x、y，缺少 distance。既然正式协议包含距离，正确示例应为：

VD,1,32.3,319.8,125.6#

或者在距离无效时：

VD,1,32.3,319.8,-1.0#

5.4 x、y 的坐标含义

通信解析层把 x、y 当作有符号数，不根据正负号猜测它们是“原始坐标”还是“中心偏差”。

项目业务层必须统一以下两种定义中的一种：

原始像素坐标：原点在图像左上角，此时 x、y 一般不为负数；

相对瞄准点的偏差：例如 x = 目标中心横坐标 - 瞄准点横坐标，此时 x、y 可以为负数。

如果需要直接用它们控制云台，更建议发送相对瞄准点的偏差。无论最终选哪一种，两端的定义和单位必须一致，解析器本身不应擅自改变正负号。

5.5 检测数据不要求逐帧应答

VD,...# 是连续遥测数据，不要求 TI 对每一帧返回应答。丢失一帧时，TI 等待下一帧即可，否则高频应答会产生无意义的通信负担。

MaixCAM2 应在每次视觉推理得到结果后发送一帧，而不是强制按 TI 的 8 ms 控制周期发送。

TI 应保存“最近一帧完整且合法的数据”。建议设置可配置的数据超时，例如 200 ms：若超过该时间没有收到新的合法检测帧，则将视觉数据标记为失效，停止使用旧坐标继续控制。

6. MaixCAM2 返回的命令应答帧

6.1 固定格式

MaixCAM2 对 TI 命令的应答格式为：

V<原命令类型>A<执行结果>#

其中：

字段

含义

V

MaixCAM2 发出的帧

<原命令类型>

当前应答对应的命令类型，如 T、D、M、Y

A

Answer，应答标志

<执行结果>

1 表示成功，0 表示失败

#

帧尾

示例：

TI → MaixCAM2：CT1#
MaixCAM2 → TI：VTA1#

VTA1# 表示：

应答的是 T 类型命令；

MaixCAM2 已经收到完整命令；

命令格式和数据合法；

MaixCAM2 已成功接受或执行该命令。

失败时：

VTA0#

其他命令的应答示例：

CD1# → VDA1#
CM1# → VMA1#
CY3.2# → VYA1#

注意区分：

VDA1#                  D 命令的应答帧，第三个字符是 A
VD,1,32.3,319.8,-1.0# 检测数据帧，第三个字符是逗号

截图中一处写成了 CTA1#。由于这条应答由 MaixCAM2 发出，正式格式必须以 V 开头，所以应使用：

VTA1#

6.2 “成功”的准确含义

应答中的 1 不是“我发出了一条回复”，而是：

该命令已经被完整接收、成功解析、通过合法性检查，并且请求的状态已经生效。

应答中的 0 表示：

已收到一条完整帧并识别出命令类型，但数据非法、当前状态不允许执行，或实际执行失败。

对于没有帧尾、严重乱码或连命令类型都无法确定的数据，直接丢弃，不发送成功应答。

6.3 每次收到命令只发送一次应答

MaixCAM2 每收到一次完整、合法的命令，只发送一次应答帧。不要在循环中连续发送多遍应答。

如果这一次应答在传输途中丢失，由 TI 在超时后重发原命令。MaixCAM2 收到重复命令后，再发送一次应答。

7. 命令超时、重发与防止重复执行

7.1 停等式通信

TI 采用“发送一条、等待应答”的停等方式：

状态需要改变时，发送一帧命令；

进入等待应答状态；

未收到当前命令的应答前，不发送下一条命令；

收到匹配的成功应答后，结束本次发送；

超时未收到应答时，重发同一条命令；

达到最大次数后仍无应答，报告通信故障。

由于当前应答帧只回传“命令类型”，没有回传原命令数据，所以必须保证任意时刻全局最多只有一条未完成命令。否则 VTA1# 无法区分它是在应答 CT1# 还是 CT0#。

7.2 推荐参数

TI 的控制周期为 8 ms。建议：

应答超时：10 个控制周期，即 80 ms
最多发送：3 次，包括首次发送和最多 2 次重发

完整行为为：

第 1 次发送 → 等待 80 ms
没有应答   → 第 2 次发送 → 等待 80 ms
没有应答   → 第 3 次发送 → 等待 80 ms
仍无应答   → 判定本次命令通信失败

收到：

V<对应命令类型>A1#

立即停止等待和重发，并报告命令成功。

收到：

V<对应命令类型>A0#

说明对方明确报告执行失败。应停止无意义的高速重发，并把失败交给上层状态机处理。

命令必须按事件发送，不能每隔 8 ms 无条件重复发送。

7.3 重复命令必须具有幂等性

应答可能丢失，因此 MaixCAM2 必须允许收到重复命令。

例如 MaixCAM2 已经执行过 CT1#，但 VTA1# 丢失，TI 会再次发送 CT1#。MaixCAM2 应当：

检查当前任务已经处于启动状态；

不重复加载模型、不重复初始化摄像头、不重复创建线程；

确认目标状态已经满足；

再发送一次 VTA1#。

也就是说，CT1# 的含义应当是“把任务状态设置为启动”，而不是“无条件重新执行一次完整初始化”。

建议摄像头和模型在 MaixCAM2 启动阶段完成初始化，使 CT1# 只负责切换任务状态，避免一次命令执行时间超过 80 ms。

8. UART 字节流接收与组帧要求

UART 收到的是连续字节流，不保证一次接收函数调用正好得到一整帧。可能出现：

第一次只收到：VD,1,-
第二次收到：32.3,319.8
第三次收到：,125.6#VTA1#

因此代码不能假设“一次 UART 接收等于一帧”，必须逐字节组帧。

8.1 推荐接收状态

接收器至少包含两个状态：

WAIT_HEADER：等待本方向合法帧头
RECEIVING：已经找到帧头，正在保存本帧字符

TI 接收端寻找帧头 V；MaixCAM2 接收端寻找帧头 C。

基本流程：

等待帧头
→ 收到帧头后清空当前帧缓冲区并保存帧头
→ 后续字符逐个写入缓冲区
→ 收到 # 后结束组帧
→ 在本地补 '\0'
→ 将完整帧交给解析函数
→ 返回等待下一帧

8.2 异常恢复

建议定义：

接收数组大小：64 字节
单帧最多保存：63 个可见字符
最后 1 字节留给本地字符串结束符 '\0'

异常处理规则：

等待帧头时，忽略其他乱码、\r 和 \n；

超过最大帧长仍未收到 #，丢弃当前帧并重新等待帧头；

接收当前帧时再次遇到本方向帧头，可认为上一帧损坏，从新帧头重新开始；

必须支持两帧紧挨着到达，例如 VTA1#VD,1,1.0,2.0,-1.0#；

任何不完整帧都不得更新业务数据；

只有整帧全部校验通过后，才能把临时解析结果一次性复制到正式数据结构。

8.3 中断中的工作必须很少

TI 的 UART 中断中只做以下工作：

读取收到的字节；

写入环形缓冲区，或者执行非常轻量的组帧状态机；

设置“有完整帧待处理”的标志。

不要在 UART 中断中执行：

sscanf()；

浮点字符串转换；

printf()；

阻塞等待；

命令对应的耗时业务；

动态内存申请。

完整帧的语法解析、数据范围检查和业务执行放在主循环或任务函数中完成。

如果检测帧可能连续到达，不能只使用一个随时会被覆盖的 frame_ready 缓冲区。应使用字节环形缓冲区、帧队列或至少双缓冲，保证主循环处理前下一帧不会覆盖上一帧。

9. 两类解析器的具体要求

9.1 MaixCAM2 的命令解析器

输入示例：

CT1#
CD0#
CM2#
CY-3.2#

解析步骤：

检查首字符是否为 C；

读取第二个字符作为命令类型；

根据类型选择整数解析器或固定一位小数解析器；

检查数据后是否立即出现 #；

检查数据值是否合法；

执行状态切换；

发送对应应答。

不得仅判断字符串中“包含 CT1”就执行，必须验证整个字符串恰好符合格式，不能带未定义的多余字符。

9.2 TI 的视觉帧解析器

收到 V 帧后，先根据前几个字符分类。

检测数据

若开头为：

VD,

则必须按固定顺序解析：

found → 逗号 → x → 逗号 → y → 逗号 → distance → #

总字段数必须准确，不能少字段或多字段。

命令应答

若格式为：

V<命令类型>A<0或1>#

则检查：

当前是否确实有一条命令正在等待应答；

应答中的命令类型是否与等待中的命令类型一致；

结果是 0 还是 1；

帧尾后没有额外字符。

不匹配的应答不得结束当前命令的等待状态。

10. 数据结构建议

TI 端可以使用类似结构：

typedef struct
{
    uint8_t found;
    int32_t x10;
    int32_t y10;
    int32_t distance10;
    uint32_t update_tick;
    uint8_t valid;
} VisionDetectionData;

命令等待状态可以使用：

typedef struct
{
    uint8_t waiting;
    char command_type;
    char frame[16];
    uint8_t frame_length;
    uint8_t send_count;
    uint16_t timeout_cycles;
    uint8_t result;
} VisionCommandRequest;

上述只是结构建议，实际字段名可以调整，但必须保留以下信息：

当前是否正在等待应答；

正在等待哪一种命令；

原始命令帧，用于原样重发；

已发送次数；

已等待的 8 ms 周期数；

最终成功、失败或超时状态。

11. 完整通信示例

11.1 正常流程

TI → MaixCAM2：CT1#                       启动任务
MaixCAM2 → TI：VTA1#                     任务启动成功

TI → MaixCAM2：CM1#                       选择模式 1（矩形）
MaixCAM2 → TI：VMA1#                     模式切换成功

TI → MaixCAM2：CD1#                       开始检测
MaixCAM2 → TI：VDA1#                     检测已经启动

MaixCAM2 → TI：VD,1,-32.3,119.8,125.6#   检测到目标
MaixCAM2 → TI：VD,1,-20.1,105.4,123.2#   下一次检测结果
MaixCAM2 → TI：VD,0,0.0,0.0,-1.0#        本次未检测到目标

TI → MaixCAM2：CD0#                       停止检测
MaixCAM2 → TI：VDA1#                     已经停止检测

TI → MaixCAM2：CT0#                       停止任务
MaixCAM2 → TI：VTA1#                     任务停止成功

11.2 应答丢失后的重发

TI → MaixCAM2：CT1#
MaixCAM2 已执行 CT1#，发送 VTA1#，但应答途中丢失

TI 等待 80 ms 后仍未收到应答
TI → MaixCAM2：CT1#                       原样重发

MaixCAM2 发现任务已经启动，不重复初始化
MaixCAM2 → TI：VTA1#                     再次应答

TI 收到匹配应答，停止重发

13. 要求代码生成 AI 遵守的实现限制

请分别生成 TI 端 C 代码和 MaixCAM2 端 Python/MaixPy 代码，并遵守以下要求。

13.1 TI MSPM0G3507 端

建议拆分为：

vision_protocol.h
vision_protocol.c

至少提供：

UART 收到一个字节时调用的入口函数；

字节环形缓冲或可靠的双缓冲组帧；

完整 V 帧分类函数；

不依赖 sscanf() 的固定一位小数解析函数；

检测数据结构；

命令发送函数；

每 8 ms 调用一次的超时与重发处理函数；

应答匹配和命令完成状态；

解析成功、格式错误、溢出、超时等状态或计数器；

几组合法帧和非法帧测试。

TI 端不得：

在 UART 中断中调用 sscanf()、printf() 或执行浮点解析；

使用动态内存；

使用阻塞式延时等待应答；

在未收到完整帧尾前更新视觉数据；

每 8 ms 无条件重复发送控制命令。

代码应将底层 UART 发送封装为独立接口，方便接入 TI SysConfig/DriverLib 已生成的 UART 实例，不要擅自假设具体 UART 名称、IRQ 名称或引脚。

13.2 MaixCAM2 端

至少提供：

非阻塞读取 UART 字节流；

C 帧组帧器；

对 T、D、M、Y 命令的严格解析；

幂等的命令状态切换；

只有在完整解析并执行后才发送的应答；

固定格式的检测数据发送函数；

使用一位小数输出 x、y、distance；

对重复命令再次应答但不重复初始化；

对非法帧的丢弃和错误统计。

Python 发送检测结果时应生成类似：

frame = f"VD,{found},{x:.1f},{y:.1f},{distance:.1f}#"
uart.write(frame.encode("ascii"))

不得自动附加换行。

13.3 v1.0 暂不包含的功能

本版协议暂不加入：

CRC 或校验和；

长度字段；

命令序号；

二进制浮点数据；

每一帧检测数据的应答；

多条控制命令并行等待。

依靠短帧、严格格式校验、帧头帧尾、超时重发和幂等执行满足当前项目需求。若后续现场电机干扰导致误码明显，再升级校验和或命令序号。
